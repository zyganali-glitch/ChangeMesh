## 0. Frozen mutual agreement

The owner and planning assistant have already agreed on the product. No generic Phase-0 interview is permitted.

### Product

**ChangeMesh — The Enterprise Change Rehearsal and Execution Fleet**

### Core promise

ChangeMesh enables enterprise agent fleets to work autonomously for hours or weeks, while escalating only the smallest irreducible set of human authority decisions.

### Product loop

**Discover → Qualify → Rehearse → Ground → Authorize → Execute → Prove → Certify**

### Competition contract

Based on the supplied competition page, project must use Gemini 3.5+ via Gemini API/Vertex AI; use at least one Google agent framework; use at least one Google Cloud infrastructure service; build/deploy a next-generation autonomous agent beyond chat; prove Google Cloud backend; submit repository, description, architecture diagram, and approximately four-minute demo; and fit Fortified Enterprise Fleet. Official rules remain binding and are reverified in P-01.

### Mandatory product properties

- autonomous by default;
- human-on-the-loop;
- Approval Compression;
- ADK runtime;
- real Gemini runtime call;
- real Google Cloud deployment;
- asynchronous/restart-safe workflow;
- trusted cross-session memory;
- Capability Passport;
- ShadowLab rehearsal;
- Reversibility Gate;
- evidence ledger/Change Evidence Passport;
- real reversible GitHub action;
- explicit fixture/simulation/real boundaries;
- credible independent product path.

### Non-goals

No automatic production merge/deploy, real customer data, formal verification, universal agent marketplace, generic workflow builder, broad multi-cloud support, unsupported security/compliance guarantee, or bulk copy of donor repos.

# P-DΩ — Continuous Donor Provenance and Reuse Integrity

**Status:** `ALWAYS_ACTIVE`
**This phase never closes before the final frozen release. It runs in addition to P-Ω.**

## P-DΩ.01 — Immutable source parity

Verify every active donor entry still points to the frozen repository, commit, and exact source paths. Detect moving-ref drift, deleted/renamed paths, or unrecorded source expansion. Any drift blocks closure until the manifest is intentionally revised.

## P-DΩ.02 — Manifest completeness parity

Verify every donor-derived changed file has a complete manifest entry with method, source paths, target paths, transformation, license state, forbidden carry-over, tests, introduction commit, reviewer, and evidence. Unmapped changed code is a blocking orphan.

## P-DΩ.03 — Source-to-target behavioral traceability

For each donor-derived target, verify the named invariant is implemented and tested, and that intentional deviations are documented. A passing generic test is insufficient when the donor invariant is untested.

## P-DΩ.04 — License, notice, and authorship parity

Verify copied/adapted content preserves required notices and that public competition documents distinguish pre-existing owner work, third-party libraries, and new ChangeMesh work. Unknown or incompatible license state blocks release.

## P-DΩ.05 — Forbidden carry-over and provider-leak audit

Search code, prompts, UI, fixtures, environment variables, docs, and tests for prohibited donor names, provider/runtime dependencies, IDs, endpoints, secrets, customer-like data, competition claims, and Phase-0/approval behavior. Remove or explicitly justify every match.

## P-DΩ.06 — Canonical implementation and anti-zombie audit

Detect duplicate evidence models, passport formats, memory engines, policy tables, connector abstractions, and dead donor-derived code. Exactly one canonical ChangeMesh authority must remain for each responsibility.

## P-DΩ.07 — Competition-period commit and disclosure parity

Bind every implemented donor component to the ChangeMesh introduction commit and ensure `docs/BUILD_PERIOD_DISCLOSURE.md`, `docs/COMPONENT_PROVENANCE.md`, Devpost text, README, and judge materials agree on what was pre-existing versus newly built.

## P-DΩ.08 — Donor test and security parity

Run all required donor behavior-parity, intentional-delta, negative, security, and forbidden-carry-over tests. Any required `FAIL` or `NOT_RUN` blocks the donor-sensitive task from `DONE`.

### Preflight Applicability Rule (P-xx.00 Tasks)

For a `P-xx.00` preflight task that explicitly forbids product implementation:
1. `P-DΩ` is still executed in full for the preflight task.
2. `P-DΩ.01`, `P-DΩ.02`, `P-DΩ.04`, `P-DΩ.05`, and `P-DΩ.06` apply normally to the artifacts, documentation, and manifest entries currently present.
3. `P-DΩ.03` during preflight verifies `SOURCE -> PLANNED TARGET` behavioral traceability, approved transformations, and defined future test suites. Once a donor-derived target is implemented in product code, the full "implemented and tested" invariant requirement applies and becomes closure-gating.
4. `P-DΩ.07` during preflight verifies that no donor component is falsely represented as implemented; `competition_introduction_commit` remains `PENDING` until implementation actually occurs in an owning task.
5. `P-DΩ.08` during preflight requires the preflight's own source-inspection, manifest-linter, auditor-review, and governance validations to pass. Future implementation parity, security, boundary, and forbidden-carry-over tests must be explicitly recorded as `DEFINED BUT NOT YET EXECUTED` and become closure-gating in their respective owning implementation tasks.
6. This preflight applicability rule **must not** permit an implemented donor-derived target to close with required tests `FAIL` or `NOT_RUN`, **must not** convert future `NOT_RUN` tests into `PASS`, and only clarifies which validations are closure-gating for documentation-only preflight tasks versus product implementation tasks. Strict implementation gates remain fully binding.
