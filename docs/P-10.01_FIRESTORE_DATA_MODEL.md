## 1. Scope and Non-Goals

### 1.1 Scope
This document defines the canonical Google Cloud Firestore persistence data model for ChangeMesh. It establishes the binding contract for:
1. **Query and Access Patterns:** Exhaustive matrix of operational queries required across the change lifecycle.
2. **Collection & Document Hierarchy:** Hierarchical tenant-partitioned collection architecture.
3. **Tenancy Boundary:** Path-based fail-closed tenancy isolation and authorization assumptions.
4. **Document Schema Matrix:** Field-level schema specifications for tenant metadata, changes, tasks, checkpoints, idempotency reservations, evidence references, approvals, and capability passports.
5. **Referential Integrity & Cascading Rules:** Parent-child ownership, orphan handling, missing reference fail-closed semantics.
6. **Concurrency & Versioning Mechanics:** Monotonic version counter and compare-and-set (CAS) optimistic concurrency specification for P-10.02.
7. **Index Specifications:** Single-field and composite index requirements, query mapping, and explicit anti-bloat index exclusions.
8. **Retention & TTL Policies:** Category-by-category operational retention policies and automated Firestore TTL field bindings.
9. **Document-Size Ceilings & Overflow Strategy:** 256 KiB ChangeMesh safety ceiling below provider 1 MiB hard limit and external hash-reference overflow rules.
10. **Security & Privacy:** Zero-secret persistence, credential isolation, schema-level `extra="forbid"` fail-closed rules.
11. **Architectural Ownership & Future Boundaries:** Clear boundaries between P-09, P-10, P-11, P-12, P-14, P-19, P-20, and P-22, with explicit deferred handoffs for P-10.02–P-10.05.

### 1.2 Non-Goals (Explicitly Excluded from P-10.01)
- **NO Repository Code:** P-10.01 does not write Python CRUD or repository classes (owned by P-10.02).
- **NO Live Firestore Operations:** No live GCP cloud writes, document creation, or index deployment.
- **NO Idempotency Runtime Implementation:** P-10.01 does not freeze the exact compound-key hashing formula or reservation execution loop (owned by P-10.03).
- **NO Checkpoint Recovery Orchestration:** P-10.01 does not implement the restart execution loop or compensation dispatch (owned by P-10.04 and P-20).
- **NO Teardown Runtime Code:** P-10.01 does not write teardown scripts or redaction interceptors (owned by P-10.05).
- **NO Domain Contract Mutation:** No Google SDK imports or provider-specific fields are added to `domain/contracts/`.
- **NO Future-Phase Runtime Leakage:** No Memory Trust scoring (P-11), Passport signing (P-12), ShadowLab execution (P-13), Approval Compression cards (P-14), GitHub writes (P-19), Saga orchestration loops (P-20), or immutable Evidence Ledger runtimes (P-22).

## 2. Canonical Inputs

The data model is derived directly from frozen domain contracts and established architectural invariants:

1. **Domain Contracts (`domain/contracts/`):**
   - `ChangeRequest` (`change_request.py`): Canonical intent snapshot (`request_id`, `title`, `description`, `target_systems`, `data_classification`, `success_criteria`, `requested_by`, `requested_at`).
   - `ChangeState` & `ALLOWED_TRANSITIONS` (`change_lifecycle.py`): 16 canonical lifecycle states with deterministic state transition validation (`RECEIVED` -> `COMPLETE`/`FAILED`/`BLOCKED`/`CANCELLED`).
   - `EvidenceRecord`, `EvidenceState`, `ExecutionEvidenceMode`, `Provenance`, `ArtifactHash`, `TraceReference` (`evidence.py`): Deterministic evidence facts, 4 evidence modes (`FIXTURE`, `SIMULATION`, `RECORDED_CLOUD`, `LIVE_WRITE`), 7 evidence states (`PASS`, `WARN`, `FAIL`, `NOT_RUN`, `SIMULATED`, `BLOCKED`, `QUARANTINED`).
   - `MemoryRecord`, `MemoryTrustStatus` (`memory.py`): Cross-session context pointers, capture/expiry timestamps, trust evidence IDs, contradiction IDs.
   - `CapabilityPassport` (`capability.py`): Deterministic agent qualification proof (`agent_id`, `agent_revision`, `qualified_capabilities`, `qualification_evidence_ids`, `expires_at`, `is_revoked`).
   - `AutonomyDecision`, `AutonomyClass`, `ApprovalCompressionCard` (`autonomy.py`): 5 autonomy classes (`AUTO_EXECUTE`, `AUTO_EXECUTE_AND_NOTIFY`, `REHEARSE_THEN_EXECUTE`, `HUMAN_AUTHORITY_REQUIRED`, `BLOCKED`), human authority slot binding, bounded decision cards.
   - `EventEnvelope` (`event_envelope.py`): Provider-neutral wire envelope (`event_id`, `change_id`, `causation_id`, `correlation_id`, `producer_id`, `producer_revision`, `idempotency_key`, `timestamp`).
   - `Machine Conventions` (`conventions.py`): `HashAlgorithm.SHA256` (64 lowercase hex characters regex `^[0-9a-f]{64}$`), `UtcDateTime` timezone-aware UTC normalization, `canonical_json_bytes`, structural secret redaction (`redact_mapping`).

2. **P-09 Event Backbone Invariants:**
   - Causal ordering owns sequencing; wall-clock timestamps are informational metadata, not causal authority.
   - Transport duplicate protection (`InMemoryDeliveryState`) and dead-letter replay idempotency (`ProcessLocalDeadLetterState`) remain process-local.
   - `execute_with_retry()` is the sole local retry owner; P-10 does not create a competing retry engine.
   - `TerminalFailureHandoff.human_authority_required` strictly remains `False`.

3. **P-10.00 Preflight & 6-Layer Idempotency Map:**
   - P-10 provides durable transactional state persistence (Layer 4) above P-09 transport delivery (Layers 1–3) and beneath P-19 external write execution (Layer 5) and P-20 saga orchestration (Layer 6).

## 4. Collection and Document Hierarchy

### 4.1 Hierarchical Path Topology
ChangeMesh adopts a **strictly hierarchical, tenant-partitioned subcollection structure**:

```
/tenants/{tenant_id}
   │
   ├── /changes/{change_id}
   │      │
   │      ├── /tasks/{task_id}
   │      │
   │      ├── /checkpoints/{checkpoint_id}
   │      │
   │      ├── /idempotency_reservations/{idempotency_key}
   │      │
   │      ├── /evidence_refs/{evidence_id}
   │      │
   │      └── /approvals/{card_id}
   │
   └── /passports/{passport_id}
```

### 4.2 Structural Rationale
1. **Natural Path-Based Tenancy Isolation:** Every document path starts with `/tenants/{tenant_id}/`. While Firestore Security Rules may be relevant to a future direct Firebase web/mobile client if one ever exists, ChangeMesh backend uses the server-side Python Firestore client authenticated through Google Cloud ADC/IAM, which bypasses Firestore Security Rules. Therefore, backend tenancy enforcement is strictly guaranteed at the application/repository boundary:
   - Authenticated/validated tenant context at the application boundary;
   - Explicit `tenant_id` passed into all repository operations;
   - Repository constructs only tenant-scoped document paths (`/tenants/{tenant_id}/...`);
   - No ambient or default tenant;
   - Malformed or missing `tenant_id` fails closed before network access;
   - Repository read operations verify embedded tenant identity where applicable;
   - Cross-tenant identifiers fail closed;
   - Least-privilege Google Cloud IAM protects database access;
   - Credentials remain adapter-only.
2. **Subcollection Partitioning Prevents Document Bloat:** By breaking tasks, checkpoints, idempotency reservations, evidence references, and approvals into subcollections, the root `/changes/{change_id}` document remains lightweight (< 8 KiB). This completely eliminates the risk of unbounded arrays hitting Firestore's 1 MiB limit.
3. **Atomic Scoped Transactions:** Firestore multi-document transactions can atomically update the root change state and insert a task/checkpoint/idempotency document in a single ACID commit within the same database partition.
4. **Scoped Teardown:** Teardown of a test or demo tenant cleanly scopes to `/tenants/{tenant_id}` and requires explicit recursive descendant document deletion (since Firestore parent deletion does not cascade to subcollections).

### 4.3 Evaluation of Rejected Alternatives

| Alternative Hierarchy | Structure | Reason for Rejection |
|---|---|---|
| **Flat Root Collections with Compound Keys** | `/changes/{tenant_id}_{change_id}`<br>`/tasks/{tenant_id}_{change_id}_{task_id}` | Rejected: Requires fragile custom string parsing to extract `tenant_id`; security and access become complex and prone to bypass; queries require composite indexes on `tenant_id` across every collection; lacks natural hierarchy. |
| **Monolithic Single Document per Change** | `/tenants/{tenant_id}/changes/{change_id}` (all tasks, checkpoints, evidence embedded as arrays) | Rejected: Unbounded growth (e.g. 50 tasks x 100 evidence references x 20 checkpoints) rapidly approaches the 1 MiB limit; write contention on the single document causes high transaction collision rates. |
| **Global Unpartitioned Collections** | `/changes/{change_id}`<br>`/tasks/{task_id}` | Rejected: Complete failure of fail-closed multi-tenancy. A single omitted query filter leaks data across tenants. |

## 5. Tenancy Boundary

### 5.1 Tenancy Key Specification
- **Tenant Identifier Format:** `tenant_id` — non-empty ASCII string matching regex `^[a-zA-Z0-9_-]{3,64}$`.
- **Standard Tenant Instances:**
  - `tenant-system`: Reserved for system agent capability passports and platform configuration.
  - `tenant-default`: Default local single-tenant development environment.
  - `tenant-demo-*`: Ephemeral demonstration and test tenants.
  - `<org_id>`: Enterprise customer tenant partitions.

### 5.2 Fail-Closed Backend Tenancy Invariants
1. **Explicit `tenant_id` Argument:** All repository interfaces in P-10.02+ MUST require `tenant_id: str` as their first positional argument. No repository method may provide a default `tenant_id` or infer it from global ambient state.
2. **Pre-Network Validation:** If `tenant_id` is missing, blank, or malformed, the repository raises `ValueError` immediately before creating a Firestore reference or initiating network I/O.
3. **Strict Path Scoping:** All document references are built strictly via `.collection("tenants").document(tenant_id)...`.
4. **Embedded Tenant Verification:** Repository read results verify that the embedded `tenant_id` in the document matches the requested `tenant_id`.
5. **Cross-Tenant Rejection:** Cross-tenant document queries or writes fail closed with `ValueError` or typed access exception.
6. **Collection Group Query Prohibition:** `collection_group()` queries across `changes`, `tasks`, or `approvals` without an equality filter on `tenant_id` are strictly prohibited in product code.
7. **Zero-Secret Storage:** No API tokens, SSH keys, private keys, service account JSON files, or GitHub credentials may ever be stored in any tenant document or field. Credentials remain adapter-only.

## 7. Referential Rules & Integrity

1. **Parent-Child Lifecycle Coupling:** Subcollections (`tasks`, `checkpoints`, `idempotency_reservations`, `evidence_refs`, `approvals`) are strictly bound to their parent `change` document path.
2. **Explicit Recursive Teardown:** Firestore parent document deletion does NOT automatically or cascade delete subcollections. Therefore, deletion or teardown of a tenant or change (P-10.05) explicitly performs recursive descendant document deletion across all subcollections to guarantee zero residual fixture state.
3. **Fail-Closed on Missing References:**
   - If a task references an `evidence_id` that is not found, the verification step FAILS CLOSED.
   - If a router queries a `passport_id` that does not exist or has `is_revoked == True` or `expires_at <= NOW()`, agent dispatch FAILS CLOSED.
   - If an approval card is missing its `authority_slot_ref` or unresolved (`resolution_status == "PENDING"`), execution remains `AWAITING_AUTHORITY` and does not proceed.
4. **Schema Version Compatibility:** Any document loaded with `schema_version != "1.0.0"` or unrecognized fields raises `ValidationError` and fails closed immediately.

## 8. Concurrency & Versioning Mechanics (Specification for P-10.02)

To prevent lost updates and race conditions across distributed agents, P-10.02 implements optimistic concurrency control (OCC):

### 8.1 Monotonic Version Token
- Every mutable document contains an integer field `version: int` initialized to `1`.
- Every successful update must atomically increment `version` by `+1`.

### 8.2 Compare-And-Set (CAS) Update Flow
```
1. READ: Load document D at path P. Record current_version = D.version.
2. COMPUTE: Validate domain transition (e.g. can_transition(D.state, new_state)).
3. WRITE (in Transaction):
   - Re-read document D_live inside transaction.
   - Assert D_live.version == expected_version (current_version).
   - If D_live.version != expected_version:
       FAIL CLOSED -> RAISE OptimisticConcurrencyError("Version conflict on document P").
   - Set D_live.version = current_version + 1.
   - Write updated document D_live.
```

### 8.3 Concurrency Error Handling and Ownership
- P-10 repository operations MUST NOT emit P-09 dead-letter records merely because an OCC conflict occurred.
- `OptimisticConcurrencyError` is a typed semantic conflict that fails closed and surfaces immediately to the calling layer.
- Zero silent overwrites are permitted.
- Zero hidden application-level infinite retry loops exist in the repository layer.
- If Firestore's internal SDK transaction retry mechanism retries transient provider `ABORTED` transactions, that behavior is bounded and adapter-local. Semantic version conflicts always raise `OptimisticConcurrencyError`.
- End-to-end workflow retry/recovery belongs to later orchestration ownership (P-20).

## 9. Index Design

### 9.1 Single-Field Indexes (Default & Exemptions)
Firestore automatically indexes all top-level document fields in ascending and descending order.
- **TTL Indexing Policy:** Native Firestore TTL is a configured database policy on native timestamp fields (`ttl_expires_at`), not an application query. TTL fields are NOT indexed merely because TTL exists. Indexes are added only for actual query requirements.
- **Exempted Fields (Index Exclusions to minimize write amplification):**
  - Large text fields: `description`, `output_summary`, `rehearsed_work_summary`, `remaining_decision_summary`, `state_reason`.

### 9.2 Composite Indexes Required
Based strictly on query patterns Q07, Q08, and Q10, exactly three composite indexes are required:

```json
{
  "indexes": [
    {
      "collectionGroup": "changes",
      "queryScope": "COLLECTION",
      "fields": [
        { "fieldPath": "state", "order": "ASCENDING" },
        { "fieldPath": "updated_at", "order": "DESCENDING" }
      ]
    },
    {
      "collectionGroup": "passports",
      "queryScope": "COLLECTION",
      "fields": [
        { "fieldPath": "agent_id", "order": "ASCENDING" },
        { "fieldPath": "agent_revision", "order": "ASCENDING" },
        { "fieldPath": "is_revoked", "order": "ASCENDING" }
      ]
    },
    {
      "collectionGroup": "approvals",
      "queryScope": "COLLECTION",
      "fields": [
        { "fieldPath": "resolution_status", "order": "ASCENDING" },
        { "fieldPath": "card_created_at", "order": "DESCENDING" }
      ]
    }
  ],
  "fieldOverrides": [
    {
      "collectionGroup": "changes",
      "fieldPath": "description",
      "indexes": []
    },
    {
      "collectionGroup": "tasks",
      "fieldPath": "output_summary",
      "indexes": []
    }
  ]
}
```

### 9.3 Indexes Deliberately NOT Created
1. **NO Collection Group Indexes:** `queryScope` is strictly `COLLECTION` (subcollection under parent), never `COLLECTION_GROUP`. Cross-tenant global queries are forbidden.
2. **NO Speculative Indexes:** Indexes on unqueried combinations (e.g. `(agent_id, status, created_at)`) are omitted.

 ## 11. Document-Size Limits & Safety Ceilings
 
 ### 11.1 Safety Ceiling
 - **Firestore Hard Limit:** 1,048,576 bytes (1 MiB).
 - **ChangeMesh Safety Ceiling:** **262,144 bytes (256 KiB)** (25% of provider hard limit).
 - **Document Size Budgets:**
   - `tenant`: < 4 KiB (normal ~ 500 B)
   - `change`: < 32 KiB (normal ~ 4–8 KiB)
   - `task`: < 16 KiB (normal ~ 2–4 KiB)
   - `checkpoint`: < 16 KiB (normal ~ 2 KiB)
   - `idempotency_reservation`: < 4 KiB (normal ~ 500 B)
   - `evidence_ref`: < 8 KiB (normal ~ 1 KiB)
   - `approval`: < 16 KiB (normal ~ 2 KiB)
   - `passport`: < 16 KiB (normal ~ 2 KiB)
 
 ### 11.2 Large Artifact Boundary & Overflow Strategy
 P-10 persists:
 - Hashes;
 - References;
 - Bounded summaries;
 - Identifiers.
 
 P-10 MUST NOT create a new GCS/BigQuery artifact-storage runtime merely because large blobs need offloading. If a payload exceeds the Firestore storage contract and no approved artifact reference exists: **FAIL CLOSED / REQUIRE AN ARTIFACT REFERENCE**. Actual Evidence Ledger / storage runtime remains later-phase work (P-22).
 
 When an approved artifact reference is used:
 1. Its SHA-256 digest is computed using `sha256_hex(data)`.
 2. The Firestore document stores strictly the `ArtifactHash` reference:
    ```json
    {
      "algorithm": "sha256",
      "digest": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
    }
    ```
 
 ### 11.3 Prohibited Stored Content
 The following data categories are **STRICTLY PROHIBITED** from entering Firestore documents:
 1. Git repository source code or commit trees.
 2. Large code patches or unified diffs (> 4 KiB).
 3. Proprietary enterprise datasets or database dumps.
 4. Raw LLM prompt-response transcripts (except bounded summaries < 4096 chars).
 5. Credentials, private keys, API tokens, service account JSON files.
 6. Binary assets, images, PDFs, compiled bytecode.

 ## 12. Security and Privacy Boundaries
 
 1. **Zero Secret Persistence:** Automated scanning and field validation reject credentials (`token`, `api_key`, `secret`, `private_key`, `service_account`). Structural redaction (`redact_mapping`) is applied before saving any error diagnostics.
 2. **Fail-Closed Deserialization:** Pydantic models configured with `extra="forbid"` immediately fail on unexpected or unversioned fields.
 3. **Tenant Boundary Enforcement:** All reads and writes must specify `tenant_id`. Cross-tenant queries and writes are blocked before dispatch.
 4. **Tamper-Evident Hashing:** State checkpoints carry SHA-256 digests; capability passports bind to qualification evidence hashes.

 ## 15. Data-Model Adversarial Review Findings
 
 An adversarial review was conducted against the data model design with the following findings and resolutions:
 
 | Review Challenge | Severity | Analysis & Finding | Resolution / Grounded Design Decision |
 |---|---|---|---|
 | **1. Unbounded Subcollections vs 1 MiB Limit** | High | Embedding tasks, checkpoints, and evidence in a single change document would breach the 1 MiB Firestore limit on complex changes. | **Resolved:** Adopted hierarchical subcollections (`/tasks`, `/checkpoints`, `/evidence_refs`, `/approvals`). Root change doc is strictly bounded to < 32 KiB. |
 | **2. Cross-Tenant Query Leakage via Collection Groups** | Critical | Using Firestore collection group queries across all tenants creates a risk of accidental cross-tenant data leakage. | **Resolved:** Prohibited unpartitioned collection group queries. All queries strictly scoped under `/tenants/{tenant_id}/`. |
 | **3. Concurrency Conflict Handling Ownership** | High | Using P-09 `execute_with_retry()` for OCC conflicts would emit dead-letter records on database race conditions. | **Resolved:** OCC conflicts fail closed, raise typed `OptimisticConcurrencyError`, and surface to caller with 0 hidden retry loops. P-10 emits 0 P-09 dead-letter records. |
 | **4. Premature Idempotency Key Freezing** | Medium | Choosing the exact idempotency hash formula in P-10.01 would violate the P-10.00 preflight deferral to P-10.03. | **Resolved:** Designated the collection space in P-10.01 while explicitly deferring the reservation identity tuple, hashing formula, and state machine to P-10.03. |
 | **5. Evidence Deletion on Saga TTL** | Critical | If Firestore TTL purges evidence references, long-term compliance audit records could be lost. | **Resolved:** Enforced strict separation between operational Firestore references (P-10) and the immutable Evidence Ledger (P-22). Saga TTL never deletes Evidence Ledger records. |
 | **6. Storing Large Diffs & Source Blobs** | High | Writing repository code or git diffs to Firestore causes document bloat and performance degradation. | **Resolved:** Established a 256 KiB safety ceiling. Artifacts > 16 KiB require an external reference. P-10 persists hashes/references and fails closed if payload exceeds limit without a reference. |
 | **7. Provider SDK in Domain Contracts** | Critical | Adding Firestore-specific fields to `domain/contracts/` would break provider neutrality. | **Resolved:** Zero modifications to `domain/contracts/`. Firestore schema models live in persistence adapter layer. |
